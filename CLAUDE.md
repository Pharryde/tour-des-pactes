# Tour des Pactes — Contexte projet

Jeu de combat au tour par tour (navigateur). Interface React pilotée par un moteur de combat Rust/WASM.

## 🛠️ COMMANDES ESSENTIELLES

**Installation initiale (ordre obligatoire) :**
```bash
cd moteur_wasm && wasm-pack build --target web && cd ..
npm install
```
(`moteur_wasm` est une dépendance npm locale `file:moteur_wasm/pkg` — le pkg doit exister AVANT `npm install`)

**Développement :**
```bash
npm run dev          # Vite, http://localhost:5173
```

**Après TOUTE modification dans `moteur_wasm/src/*.rs` :**
```bash
cd moteur_wasm
cargo check --target wasm32-unknown-unknown   # vérif rapide sans rebuild complet
wasm-pack build --target web                  # OBLIGATOIRE avant de tester côté TS
```
⚠️ Sans ce rebuild, le HMR de Vite ne recharge PAS le binaire `.wasm` — le TS compile mais tourne sur l'ancien moteur.

**Build / qualité / déploiement :**
```bash
npm run build         # tsc -b && vite build
npm run lint           # eslint .
npm test               # vitest run (une passe, PAS de mode watch)
npm run preview        # sert le build de prod en local
```
- Déploiement : Vercel (auto-détecte Vite sur push git, pas de config locale)
- Avant de considérer une tâche terminée : `tsc -b` + `eslint .` + `npm test` propres, `cargo check` si Rust touché, **et test manuel dans le navigateur** (compilation ≠ fonctionnement)
- ⚠️ **Ne jamais lancer de commande longue ou bavarde en console** (`npm run dev`, `vite`, tout mode `--watch`) : le pseudo-terminal Windows (ConPTY) de cette machine se fige quand un processus écrit en continu, ce qui plante l'application. Le serveur de dev est lancé par l'utilisateur dans son propre terminal ; pour la preview, utiliser `preview_start` avec une **URL** (`http://localhost:5173`), jamais avec un `name`.

## 🏗️ ARCHITECTURE ET STACK

**Stack :** React 19 + TypeScript + Vite · Rust → WebAssembly (wasm-bindgen) · `localStorage` (source de vérité immédiate) + Supabase (sauvegarde cloud, miroir asynchrone)
Pas de state manager externe, pas de router — état 100% dans un hook custom, écrans gérés par un type union.

⚠️ **Dev local nécessite un `.env.local`** (non commité, voir `.gitignore` — règle `*.local`) avec `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` et `VITE_TURNSTILE_SITE_KEY`. Attention à l'endroit où ça casse : `npm run dev` démarre **normalement** même sans ces variables (Vite ne les valide pas au démarrage et n'affiche aucune erreur). C'est la **page** qui casse au chargement dans le navigateur — écran blanc + erreur console — parce que `src/utils/supabaseClient.ts` appelle `createClient()` au niveau module. Ne pas chercher l'erreur dans le terminal : elle n'y apparaîtra jamais.

**Dossiers clés :**
- `moteur_wasm/src/` — moteur de combat (source de vérité des calculs)
  - `entite.rs` — structs `Entite`/`StructureEtage` (miroir exact de `src/types.ts`)
  - `combat.rs` — calculs purs : dégâts, combo, esquive
  - `boss_data.rs` — données des étages/monstres/boss (aucune logique, juste des données)
  - `lib.rs` — bindings `wasm_bindgen` exposés au JS (`jouer_tour`, `get_donnees_etages`)
- `src/hooks/useGameState.ts` — **le cerveau de l'app** : tout l'état persistant (`localStorage`) + toute la logique métier (actions, progression, pactes)
- `src/hooks/useSauvegardeCloud.ts` — synchro Supabase isolée (session anonyme, restauration, autosauvegarde) ; ne connaît aucune règle du jeu, seulement QUAND l'état a changé
- `src/hooks/useCombatResume.ts` — reprise d'un combat après rechargement de page. Tout l'état tient dans **une seule** clé `tdp_combat_actif` (un état partiellement réécrit serait de toute façon incohérent) ; passer par `effacerEtatCombat()` plutôt que de manipuler le nom de la clé depuis l'extérieur
- ⚠️ **Le journal de combat est plafonné à `LIMITE_LOGS` (300)** dans `useGameState.ts`, via un `setHistoriqueLogs` qui enveloppe le setter brut — c'est le seul point qui garantit la borne pour la douzaine d'appelants. Sans elle, le coût est quadratique : chaque ligne re-sérialise le tableau entier dans localStorage, ajoute un nœud DOM au journal rendu, et regonfle l'instantané cloud
- `src/components/` — écrans/composants de rendu uniquement (pas de logique métier lourde ; délèguent via callbacks reçus en props)
- `src/utils/` — fonctions pures sans état (pactes, animations, calculs de récompense/compétences) ; contient aussi `supabaseClient.ts` (client singleton), `sauvegardeCloud.ts` (lecture/écriture du snapshot cloud) et `versionApp.ts` (`APP_VERSION`, partagée entre purge locale et rejet cloud)
- `src/utils/*.test.ts` — tests Vitest co-localisés, **fonctions pures uniquement** (aucun JSX/WASM/DOM, d'où une `vitest.config.ts` distincte qui ne charge pas le plugin React). Priorité aux calculs miroirs du moteur Rust, où une divergence rend l'affichage mensonger sans rien casser de visible
- `supabase/migrations/` — schéma SQL de la base Supabase, déployé automatiquement sur `main` via l'intégration GitHub Vercel↔Supabase (pas de CLI/push manuel nécessaire)
- `src/types.ts` — types partagés, DOIT rester en miroir de `entite.rs` (camelCase TS ↔ snake_case Rust via `serde(rename_all = "camelCase")`)
- `public/sprites/<personnage>/` — feuilles de sprites pixel art (une par animation)
- `public/images/` — illustrations de cinématique de boss (une par pacte)

**Pas de pages classiques (Accueil/Tarifs/Contact)** — jeu à écran unique. Navigation = type `Ecran` (union de string literals dans `types.ts`) + rendu conditionnel dans `App.tsx`.

## 📏 CONVENTIONS DE CODE

- **Langue : tout en français** (variables, fonctions, composants, commentaires). Anglais uniquement pour mots-clés techniques/libs.
- Composants : PascalCase (`CombatArene.tsx`). Hooks : camelCase préfixé `use`. Utils : camelCase, un fichier = un domaine.
- **Synchro Rust ↔ TS obligatoire** : toute nouvelle propriété sur `Entite` doit exister des deux côtés (snake_case Rust / camelCase TS).
- **Registre de pactes** : source unique de vérité = `PACTES_REGISTRY` dans `utils/pactes.ts`. Ajouter une entrée suffit à l'activer partout.
- **Nouvel étage** : ajouter `get_etage_xxx()` dans `boss_data.rs` + l'enregistrer dans `get_tous_les_etages()`. Réutiliser les helpers existants (`esquive_std()`, `kit_complet()`, `nom_boss*()`...) plutôt que des littéraux dupliqués.
- **Style** : classes CSS uniquement, tout dans `App.css`/`index.css` (sections commentées par écran). Style inline réservé aux valeurs calculées à l'exécution (ex: largeur de barre de progression). Un seul breakpoint responsive à 768px — toujours vérifier l'absence de débordement horizontal et l'alignement entre cartes symétriques (joueur/monstre) après un changement visuel.
- **React** : jamais de `setState` synchrone dans un `useEffect` (règle ESLint active) — utiliser l'ajustement d'état pendant le rendu quand la condition redevient fausse d'elle-même après mise à jour. `prefer-const` actif.
- **Commentaires** : uniquement pour un "pourquoi" non-évident (contrainte cachée, workaround). Pas de commentaires qui répètent le code.
- **Modèle à respecter pour un nouveau fichier** : une responsabilité claire (composant = rendu, hook = état+logique, util = fonction pure), pas de mélange logique métier / JSX au-delà de l'orchestration.

Ne révèle jamais LAQUELLE des 4 synergies est visée (conforme au principe "synergies = secret à découvrir") — se contente de désigner le Pacte manquant.
- Inventaire : chaque section (Niveau I / Niveau II) n'affiche la liste COMPLETE de son niveau (`Object.keys(PACTES_REGISTRY)`, source de vérité unique) qu'une fois que le joueur possède au moins un Pacte de ce niveau (`possedeLvl1`/`possedeLvl2` — sinon la section entière reste masquée, pas seulement les cartes). Une fois affichée, les Pactes non débloqués de la section apparaissent grisés (`.pacte-carte--verrouille`, `opacity`+`grayscale`, non cliquable) avec leur nom mais sans leur effet (`???` à la place de la description). Les deux niveaux sont gérés indépendamment (posséder un Pacte de Niveau I ne révèle pas la section Niveau II, et vice-versa).
- Sauvegarde cloud Supabase (`utils/supabaseClient.ts`, `utils/sauvegardeCloud.ts`, câblée dans `useGameState.ts`) : `localStorage` reste la source de vérité immédiate, Supabase devient un miroir asynchrone identifié par un utilisateur anonyme (`signInAnonymously`, aucun compte/mot de passe côté joueur). Un instantané JSON des ~35 clés `tdp_*` gérées par `useGameState` (progression + méta-progression + stats de run) est poussé en `upsert` vers la table `sauvegardes` (RLS stricte sur `auth.uid() = user_id`) après une accalmie de `DELAI_DEBOUNCE_MS` (3s), plafonnée à `DELAI_PLAFOND_MS` (30s) — sans ce plafond, les dépendances de l'effet changeant à chaque tour de combat, un joueur rapide réarmerait le minuteur sans fin et ne sauvegarderait jamais. Plus un flush best-effort sur `visibilitychange`. ⚠️ **`setCloudUserId` doit impérativement rester APRÈS la tentative de restauration** : c'est lui qui arme l'autosauvegarde, et le poser avant l'appel réseau laisse un réseau lent écraser la sauvegarde cloud avec l'état local encore vide (perte de progression). L'horodatage `mis_a_jour_le` n'est pas envoyé par le client : un déclencheur Postgres l'impose côté serveur. La colonne `version` porte `APP_VERSION` (`utils/versionApp.ts`) et une sauvegarde d'une autre version est **refusée** à la restauration — sans ce refus, la purge locale déclenchée par un incrément de version serait aussitôt annulée par la restauration cloud, qui réinjecterait les données obsolètes. Exclut volontairement la clé `tdp_combat_actif` de `useCombatResume.ts` (écriture à chaque tick de combat, trop bavard et purement éphémère). Au tout premier lancement sur un appareil dont l'état local est "vierge" (même garde-fou que le déclenchement du tuto), si une sauvegarde cloud existe déjà pour cette session anonyme, elle est restaurée dans `localStorage` puis la page est rechargée (plus simple/sûr que d'appeler individuellement les ~30 setters du hook). Limite connue acceptée pour cette v1 : l'identité anonyme vit elle-même dans le `localStorage` du navigateur, donc ça protège contre une perte locale (storage corrompu/vidé, purge de version) mais pas contre un vrai changement d'appareil sans avoir jamais eu de session commune — évolution possible plus tard via un upgrade vers un compte email (fonctionnalité native de Supabase Auth, pas de migration de schéma nécessaire).
- Protection Cloudflare Turnstile sur l'inscription anonyme (`utils/turnstile.ts`, script chargé dans `index.html`, jeton passé à `signInAnonymously` depuis `assurerSessionAnonyme`) : évite l'abus de création de sessions anonymes qui gonflerait la base/les quotas MAU gratuits (recommandation du dashboard Supabase). Mode "Invisible" côté Cloudflare = aucun widget visible pour un visiteur légitime. Le jeton n'est demandé qu'à la toute première création de session par navigateur (jamais au retour d'un joueur déjà connu, cf. le court-circuit sur `getSession()` existant). Nécessite `VITE_TURNSTILE_SITE_KEY` (clé publique, `.env.local`/Vercel) + la clé secrète correspondante configurée côté Supabase (Authentication → Attack Protection → Captcha). Dégradation gracieuse si absent/échoue : `signInAnonymously` est quand même tenté sans jeton (Supabase le rejette lui-même si la protection captcha est active côté projet — la sauvegarde cloud reste alors simplement inactive pour ce joueur, le jeu continue de fonctionner en localStorage pur). ⚠️ **Toute attente sur Turnstile doit rester bornée** (`DELAI_MAX_SCRIPT_MS` / `DELAI_MAX_TOKEN_MS`) : le script vient d'un tiers que bloqueurs de pub et réseaux d'entreprise coupent volontiers, et sans échéance la promesse ne se résout jamais — `assurerSessionAnonyme` reste suspendue et la sauvegarde cloud meurt en silence, sans erreur remontée.
- En-têtes de sécurité HTTP dans `vercel.json` (`X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` en vigueur ; CSP volontairement en **`Report-Only`** pour l'instant). La CSP doit conserver `'wasm-unsafe-eval'` dans `script-src` (le moteur WASM ne s'instancie pas sans), `https://challenges.cloudflare.com` dans `script-src`/`frame-src` (Turnstile), `https://*.supabase.co` + `wss://*.supabase.co` dans `connect-src`, et `'unsafe-inline'` dans `style-src` (styles inline calculés à l'exécution, cf. conventions). Basculer en `Content-Security-Policy` (sans `-Report-Only`) une fois vérifié qu'aucune violation n'apparaît en console sur le déploiement.
