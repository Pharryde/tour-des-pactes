# Tour des Pactes — Contexte projet

Jeu de combat au tour par tour (navigateur). Interface React pilotée par un moteur de combat Rust/WASM.

📖 **Les règles du jeu elles-mêmes sont dans [`REGLES.md`](REGLES.md)** — document lisible rangé par catégorie (tour de combat, actions, combo, armure, esquive, brûlure/poison, étages, Pactes, synergies, bénédictions, XP…). Ce fichier-ci ne garde que les contraintes techniques et les pièges d'implémentation. **Toute modification de règle doit être répercutée dans les deux.**

## 🛠️ COMMANDES ESSENTIELLES

**Installation initiale (ordre obligatoire) :**
```bash
cd moteur_wasm && wasm-pack build --target web && cd ..
npm install
```
(`moteur_wasm` est une dépendance npm locale `file:moteur_wasm/pkg` — le pkg doit exister AVANT `npm install`)

**Développement :**
```bash
npm run dev          # Vite, http://localhost:5173
```

🩺 **`node_modules` se corrompt sur cette machine.** Symptômes : page blanche + `Failed to resolve import "<dépendance>"` en console, ou `ERR_MODULE_NOT_FOUND` au lancement des tests. Signature constante : **les fichiers finissant par `.js` sont absents** alors que leurs voisins `.d.ts`, `.js.map`, `.mjs` et `.html` sont intacts — un `dist/` ne contenant que des `.map` et des `.d.ts` est le tell. Constaté le 2026-08-08 sur `@supabase/*`, puis sur l'arbre de `vitest` (`chai`, `tslib`, `magic-string`…).

⚠️ **Un `npm install` incrémental (sur un `node_modules` existant) peut lui-même provoquer la casse** : c'est ce qui a détruit l'arbre de `vitest`, qui fonctionnait juste avant. Antivirus et cache npm ont été écartés (aucun événement Defender, accès contrôlé aux dossiers et règles ASR désactivés, `npm cache verify` intact) — cause racine non identifiée.

**Réparation fiable** : supprimer `node_modules` **en entier** puis `npm install` (une réinstallation partielle ne suffit pas). Purger aussi `node_modules/.vite`, dont le cache de pré-bundling garde des références vers l'ancien état. **Détection** : scanner les points d'entrée de tous les paquets (`main` de chaque `package.json` doit exister) — un arbre sain donne 0 manquant.

**Après TOUTE modification dans `moteur_wasm/src/*.rs` :**
```bash
npm run wasm
```
Ce script enchaîne le build Rust, la génération des liaisons, **et la purge de `node_modules/.vite`** — sans cette dernière, Vite continue de servir l'ancien moteur depuis son cache de pré-bundling. `node_modules/moteur_wasm` étant une jonction vers `moteur_wasm/pkg`, aucun `npm install` n'est nécessaire ensuite. Pour une simple vérification de compilation sans rebuild : `cd moteur_wasm && cargo check --target wasm32-unknown-unknown`.

🚫 **`wasm-pack` ne fonctionne plus sur cette machine** (constaté le 2026-08-10) : Smart App Control est actif en mode bloquant (`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy` → `VerifiedAndReputablePolicyState = 1`) et refuse `wasm-pack.exe`, un binaire non signé portant la marque `Zone.Identifier` (« téléchargé depuis Internet »). Ne pas désactiver Smart App Control pour contourner ça : Windows ne permet pas de le réactiver ensuite sans réinstallation.

Les deux commandes ci-dessus reproduisent exactement ce que faisait wasm-pack. `wasm-bindgen` (CLI) doit être installé à la version EXACTE du `Cargo.lock` — sinon les liaisons générées sont incompatibles :
```bash
cargo install wasm-bindgen-cli --version 0.2.126 --locked
```
Compilée localement, elle n'a pas de marque Internet et passe donc Smart App Control. `pkg/package.json` n'est pas régénéré par `wasm-bindgen` mais il existe déjà et n'a pas à changer.

L'étape `wasm-opt` de wasm-pack est perdue au passage ; elle est compensée par le profil `[profile.release]` de `moteur_wasm/Cargo.toml` (`opt-level = "s"`, `lto`, `codegen-units = 1`, `strip`), qui donne un binaire un peu **plus petit** que l'ancien (132 Ko contre 138 Ko). Ne pas y ajouter `panic = "abort"` : on perdrait les messages de panique que `CombatArene` remonte en console.
⚠️ Sans ce rebuild, le HMR de Vite ne recharge PAS le binaire `.wasm` — le TS compile mais tourne sur l'ancien moteur.

**Build / qualité / déploiement :**
```bash
npm run build         # tsc -b && vite build
npm run lint           # eslint .
npm test               # vitest run (une passe, PAS de mode watch)
npm run preview        # sert le build de prod en local
```
- Déploiement : Vercel (auto-détecte Vite sur push git, pas de config locale)
- Avant de considérer une tâche terminée : `tsc -b` + `eslint .` + `npm test` propres, `cargo check` si Rust touché, **et test manuel dans le navigateur** (compilation ≠ fonctionnement)
- ⚠️ **Ne jamais lancer de commande longue ou bavarde en avant-plan** (`npm run dev`, `vite`, tout mode `--watch`) : le pseudo-terminal Windows (ConPTY) de cette machine se fige quand un processus écrit en continu, ce qui plante l'application. Lancer en **tâche de fond avec la sortie redirigée vers un fichier log**, puis lire le log — jamais en avant-plan.
- ⚠️ **Ne jamais ouvrir le panneau navigateur intégré (`preview_start`)** : chaque ouverture d'un nouveau panneau a planté l'application (2 occurrences le 2026-08-08). Le serveur Vite, lui, survivait au crash et écoutait toujours après coup — c'est bien le panneau le coupable, pas le serveur ni le port. Corollaire : déplacer le serveur hors de `localhost` ne règle rien et coûte cher, le navigateur intégré refusant en plus ses outils de lecture sur toute origine non-`localhost`.
- **Vérification dans le navigateur** : passer par le vrai Chrome de l'utilisateur (outils `claude-in-chrome`). Serveur dédié en tâche de fond, sur un port distinct de celui de l'utilisateur (5173) :
  ```bash
  npx vite --host 127.0.0.1 --port 5174 --strictPort > /chemin/vers/vite.log 2>&1
  ```
  Le `--host 127.0.0.1` n'est pas décoratif : sans lui Vite n'écoute qu'en IPv6 (`::1`) et `http://127.0.0.1:5174` est injoignable. Le premier `navigate` peut expirer côté outil alors que la navigation a réussi — vérifier avec `tabs_context_mcp` avant de conclure à un échec.

## 🏗️ ARCHITECTURE ET STACK

**Stack :** React 19 + TypeScript + Vite · Rust → WebAssembly (wasm-bindgen) · `localStorage` (source de vérité immédiate) + Supabase (sauvegarde cloud, miroir asynchrone)
Pas de state manager externe, pas de router — état 100% dans un hook custom, écrans gérés par un type union.

⚠️ **Dev local nécessite un `.env.local`** (non commité, voir `.gitignore` — règle `*.local`) avec `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` et `VITE_TURNSTILE_SITE_KEY`. Attention à l'endroit où ça casse : `npm run dev` démarre **normalement** même sans ces variables (Vite ne les valide pas au démarrage et n'affiche aucune erreur). C'est la **page** qui casse au chargement dans le navigateur — écran blanc + erreur console — parce que `src/utils/supabaseClient.ts` appelle `createClient()` au niveau module. Ne pas chercher l'erreur dans le terminal : elle n'y apparaîtra jamais.

**Dossiers clés :**
- `moteur_wasm/src/` — moteur de combat (source de vérité des calculs)
  - `entite.rs` — structs `Entite`/`StructureEtage` (miroir exact de `src/types.ts`)
  - `combat.rs` — calculs purs : dégâts, combo, esquive
  - `boss_data.rs` — données des étages/monstres/boss (aucune logique, juste des données)
  - `lib.rs` — bindings `wasm_bindgen` exposés au JS (`jouer_tour`, `get_donnees_etages`)
- `src/hooks/useGameState.ts` — **le cerveau de l'app** : tout l'état persistant (`localStorage`) + toute la logique métier (actions, progression, pactes)
- `src/hooks/useSauvegardeCloud.ts` — synchro Supabase isolée (session anonyme, restauration, autosauvegarde) ; ne connaît aucune règle du jeu, seulement QUAND l'état a changé
- `src/hooks/useCombatResume.ts` — reprise d'un combat après rechargement de page. Tout l'état tient dans **une seule** clé `tdp_combat_actif` (un état partiellement réécrit serait de toute façon incohérent) ; passer par `effacerEtatCombat()` plutôt que de manipuler le nom de la clé depuis l'extérieur
- ⚠️ **Le journal de combat est plafonné à `LIMITE_LOGS` (300)** dans `useGameState.ts`, via un `setHistoriqueLogs` qui enveloppe le setter brut — c'est le seul point qui garantit la borne pour la douzaine d'appelants. Sans elle, le coût est quadratique : chaque ligne re-sérialise le tableau entier dans localStorage, ajoute un nœud DOM au journal rendu, et regonfle l'instantané cloud
- `src/components/` — écrans/composants de rendu uniquement (pas de logique métier lourde ; délèguent via callbacks reçus en props)
- `src/utils/` — fonctions pures sans état (pactes, animations, calculs de récompense/compétences) ; contient aussi `supabaseClient.ts` (client singleton), `sauvegardeCloud.ts` (lecture/écriture du snapshot cloud) et `versionApp.ts` (`APP_VERSION`, partagée entre purge locale et rejet cloud)
- `src/utils/*.test.ts` — tests Vitest co-localisés, **fonctions pures uniquement** (aucun JSX/WASM/DOM, d'où une `vitest.config.ts` distincte qui ne charge pas le plugin React). Priorité aux calculs miroirs du moteur Rust, où une divergence rend l'affichage mensonger sans rien casser de visible
- `supabase/migrations/` — schéma SQL de la base Supabase, déployé automatiquement sur `main` via l'intégration GitHub Vercel↔Supabase (pas de CLI/push manuel nécessaire). ⚠️ **L'organisation contient DEUX projets Supabase** : `kmccjfzqakmsjmxyisrq` (le vrai — pointé par `.env.local` ET par le bundle de prod) et `wzeseotszumzkpnkptbn` / `tour-des-pactes-db`, un orphelin créé par le Vercel Marketplace que rien ne référence (d'où sa mise en pause automatique après 7 jours d'inactivité). Vérifier la référence de projet avant de conclure quoi que ce soit sur la sauvegarde cloud — et se rappeler que le vrai projet est soumis à la même règle des 7 jours, sa mise en pause tuant la synchro **en silence** (`console.error` seul, dégradation gracieuse voulue)
- `supabase/analyses.sql` — requêtes d'analyse à coller dans le SQL Editor. **Pas une migration** : jamais exécutée automatiquement, ne modifie rien
- `src/types.ts` — types partagés, DOIT rester en miroir de `entite.rs` (camelCase TS ↔ snake_case Rust via `serde(rename_all = "camelCase")`)
- `public/sprites/<personnage>/` — feuilles de sprites pixel art (une par animation)
- `public/images/` — illustrations de cinématique de boss (une par pacte)

**Pas de pages classiques (Accueil/Tarifs/Contact)** — jeu à écran unique. Navigation = type `Ecran` (union de string literals dans `types.ts`) + rendu conditionnel dans `App.tsx`.

## 📏 CONVENTIONS DE CODE

- **Langue : tout en français** (variables, fonctions, composants, commentaires). Anglais uniquement pour mots-clés techniques/libs.
- Composants : PascalCase (`CombatArene.tsx`). Hooks : camelCase préfixé `use`. Utils : camelCase, un fichier = un domaine.
- **Synchro Rust ↔ TS obligatoire** : toute nouvelle propriété sur `Entite` doit exister des deux côtés (snake_case Rust / camelCase TS).
- **Registre de pactes** : source unique de vérité = `PACTES_REGISTRY` dans `utils/pactes.ts`. Ajouter une entrée suffit à l'activer partout.
- **Nouvel étage** : ajouter `get_etage_xxx()` dans `boss_data.rs` + l'enregistrer dans `get_tous_les_etages()`. Réutiliser les helpers existants (`esquive_std()`, `kit_complet()`, `nom_boss*()`...) plutôt que des littéraux dupliqués.
- **Style** : classes CSS uniquement, tout dans `App.css`/`index.css` (sections commentées par écran). Style inline réservé aux valeurs calculées à l'exécution (ex: largeur de barre de progression). Un seul breakpoint responsive à 768px — toujours vérifier l'absence de débordement horizontal et l'alignement entre cartes symétriques (joueur/monstre) après un changement visuel.
- ⚠️ **`.ecran` se dimensionne en `min-height: calc(100dvh - 20px)`, jamais en `height`/`max-height`.** Avec une hauteur imposée, tout contenu plus grand que l'écran est rogné en haut ET en bas sans pouvoir y accéder (les écrans étant centrés verticalement) — c'est ce qui coupait plusieurs écrans sur mobile. Et `dvh` (pas `vh`) parce que `vh` fige la hauteur barres d'outils masquées, donc déborde toujours de la zone réellement visible sur mobile. Corollaire : un enfant ne peut plus compter sur `height: 100%` (le parent n'a plus de hauteur définie) — utiliser `flex: 1`, comme `.arene-wrapper`.
- **React** : jamais de `setState` synchrone dans un `useEffect` (règle ESLint active) — utiliser l'ajustement d'état pendant le rendu quand la condition redevient fausse d'elle-même après mise à jour. `prefer-const` actif.
- **Commentaires** : uniquement pour un "pourquoi" non-évident (contrainte cachée, workaround). Pas de commentaires qui répètent le code.
- **Modèle à respecter pour un nouveau fichier** : une responsabilité claire (composant = rendu, hook = état+logique, util = fonction pure), pas de mélange logique métier / JSX au-delà de l'orchestration.

- **4 étages ajoutés (Froid, Foudre, Feu, Poison)** — la Tour compte 12 étages, donc 48 salles par run, et le Gardien Absolu monte à 1200 PV. Chaque Gardien donne un Pacte qui retourne sa mécanique contre les monstres (`PACTES_REGISTRY`).
  - **Froid** (`actions_resolution_inversee`, `actions_gelees`) : casse le postulat du simultané. Sur N créneaux tirés au hasard, le porteur agit AVANT l'autre — une Défense programmée sur ce créneau arrive trop tard. Le lvl1 gèle une action à la place (annulée : ni garde, ni dégâts, ni avancée de combo), le lvl2 cumule les deux. ⚠️ Un pouvoir porté des **deux** côtés s'annule : seul l'écart compte.
  - **Foudre** (`multiplicateur_degats_si_armure`) : x1,5/x2/x3 sur les dégâts **totaux** tant que la cible porte de l'armure — Précise comprise, qui garde par ailleurs son contournement. Se défendre contre lui est un piège.
  - **Feu** (`multiplicateur_brulure` → `brulure_active`) : ⚠️ l'**Attaque** (et elle seule) cesse de blesser directement — elle devient une brûlure qui **s'accumule** coup après coup (`+=`, pas un rafraîchissement) et se résout en fin de tour, absorbée par l'armure restante puis divisée par deux. Les occupants de l'étage n'ont pas la Précise (`kit_sans_precise`) : toutes leurs offensives passent donc en brûlure.
  - **Poison** (`multiplicateur_poison` → `poison_actif`) : miroir exact — la **Précise** (et elle seule) devient du poison. Traverse l'armure et ne décroît jamais. Les doses **s'additionnent dans le tour** (accumulateur `poison_sur_*` dans `jouer_tour`) **comme d'un tour à l'autre** (10 au tour 1 puis 10 au tour 2 = 20) : c'est ce qui force à conclure vite. Les occupants de l'étage n'ont pas l'Attaque (`kit_sans_attaque`).

À 1.0 dès le Niveau I, le Pacte serait strictement supérieur à l'action qu'il remplace (brûlure qui s'empile, poison qui ignore l'armure) — d'où la conversion partielle.

C'est ce qui a remplacé l'ancien `solderBrulure()` côté TS, supprimé. Les deux états sont ensuite nettoyés entre deux salles (`useGameState`), ils ne se transportent jamais d'un combat au suivant.

Le compteur démarre à `tdp_runs_terminees` (et non 0) pour ne pas réutiliser les numéros déjà journalisés chez un joueur installé.
  - Un **abandon** (`gererAbandon`) est journalisé mais ne passe pas par `capturerStatsFinRun` : il ne compte ni pour `runsTerminees` (qui cadence les apparitions du Chat) ni pour le record. Garde `listeEtages.length > 0` pour ne pas enregistrer de run fantôme.
  - Zones de Repos : **deux** compteurs de run, `tdp_repos_proposes_run` et `tdp_repos_pris_run`. Au-delà de la 1re visite d'une run seules 3 des 5 options sont tirées, donc un choix peu pris peut n'avoir été que peu **proposé** — sans le dénominateur, le taux d'utilisation reflète surtout la chance du tirage.
  - Actions et combos : `ajouterStatsTour` prend désormais un objet `StatsTour` (elle avait 3 arguments, elle en aurait 9). `CombatArene` réutilise le suivi de combo qu'il fait **déjà pour l'affichage** (`localComboJ`/`localComboM`), donc gel de l'Étage du Froid compris. Les actions programmées comptent les créneaux gelés (le joueur les a bien choisis) ; les combos ne les comptent pas (le moteur y saute le calcul de palier, il n'y a aucun palier à mesurer).
  - ⚠️ **Le combo est stocké en SOMME + NOMBRE, jamais en moyenne déjà calculée** (`combo_somme_*`/`combo_actions_*`) : une moyenne de moyennes est fausse dès qu'on agrège des runs de longueurs différentes, alors que `sum(somme)/sum(actions)` reste exact. Le combo des **monstres** est mesuré aussi : leurs actions étant tirées au hasard, leur moyenne est l'étalon de ce qu'on obtient sans chercher à enchaîner — c'est l'écart joueur/monstres qui dit si la mécanique est comprise.
- ⚠️ **Turnstile refuse `127.0.0.1`** (erreur 110200, domaine non autorisé sur le widget Cloudflare) : en dev local, `signInAnonymously` est donc rejeté par Supabase (« captcha protection: request disallowed ») et **la sauvegarde cloud comme le journal de runs sont inactifs**, silencieusement. La prod (`tour-des-pactes.vercel.app`) n'est pas concernée, son domaine étant autorisé. Pour tester ces chemins en local, ajouter `127.0.0.1` et `localhost` aux hostnames du widget dans le dashboard Cloudflare.
